# 基于强化学习（GRPO）优化本地 LLM 视觉导航的技术实现详细步骤

本文档的创新方案：**使用开源本地大模型（Qwen/Llama）挂载 LoRA 适配器，在 NavGPT 仿真环境中进行在线交互式 GRPO 训练，通过「基础导航奖励 + 跨模态语义对齐奖励 + 思维质量奖励」三类复合奖励，同步优化 LLM 的动作准确率与思考质量，弥补视觉转文本信息损失，提升规划可解释性。**

> **实现修订说明：** 下文对模型模板、环境接口和 GRPO 接入方式的
> 修订不改变上述创新点。修订目的是确保零样本推理、在线轨迹收集和
> LoRA 推理共享同一状态与动作协议，使三类创新奖励能够真正作用于
> 同一个策略输出。

------

## 阶段一：模型准备与本地推理打通（脱离 API 依赖）

**目标：** 让本地开源模型完全替代 `nav_src/agent.py` 中的 OpenAI 调用，并保持「思考 + 动作」的结构化输出格式，为后续思维奖励优化预留接口。

### 第一步：从 HuggingFace / ModelScope 下载本地开源模型

当前论文主模型统一为 **Qwen2.5-14B-Instruct-1M**：

- **主力训练模型：** `Qwen/Qwen2.5-14B-Instruct-1M` 的 Hugging Face
  Safetensors 权重，用于 LoRA/GRPO 训练；
- **主力 GGUF 基线：**
  `Qwen2.5-14B-Instruct-1M-Q4_K_M.gguf`，与主模型参数规模同为 14B，
  但属于 llama.cpp 的 4-bit 推理量化格式，不能直接作为 PEFT 训练权重；
- **调试用备选模型：** Qwen2.5 0.5B/1.5B/7B，仅用于显存不足时快速
  排查训练框架 Bug，不作为论文主结果模型；
- **辅助模型：** `openai/clip-vit-large-patch14`，用于跨模态语义对齐奖励的特征提取

HF 模型不是单个 `.hf` 文件，而是包含配置、tokenizer、权重索引和多份
`.safetensors` 分片的目录。`Q4_K_M` 是 GGUF 量化类型，不是 HF 模型名。

### 第二步：改造 NavGPT 的 LLM 接入层

原版 NavGPT 基于 OpenAI API 开发，需重构 LLM 接入层，适配本地模型与结构化输出要求：

1. **编写多后端模型包装器**：
   - `openai`：在线模型接收后端中性的导航 Prompt；
   - `hf`：基于 Hugging Face `transformers` 加载可训练权重，并调用
     tokenizer 的 `apply_chat_template()`；
   - `gguf`：基于 `llama.cpp` 的 chat completion 运行量化模型，仅作为
     推理/基线后端，不能直接用于 PEFT 训练；
   - 三个后端返回相同的纯文本策略输出，统一进入同一个解析器。

2. 适配 Prompt 与输出模板：

   - 导航 Prompt 本身保持后端中性，模型专属 Chat Template 只在各后端
     包装器中应用，避免 HF/GGUF/OpenAI 出现双重模板；

   - 强制约束模型输出格式为：
     `<Think>推理思考内容</Think>\n<Action>action_maker("viewpoint_id")</Action>`
     或 `<Think>停止依据</Think>\n<Action>Finish!</Action>`；
   - 使用统一解析器将输出归一化为 `thought / action_type /
     viewpoint_id`，推理执行和思维质量奖励共同使用这一结果。
   - 限制 Think 的最大 token/词数并要求紧接 Action，防止长思考挤掉
     动作或通过冗长文本进行奖励投机。

3. **统一状态输入来源**：
   - `planner`（当前默认）：先根据原始 instruction 生成 action plan，再
     将 action plan 作为导航策略输入；
   - `instruction`：直接使用原始指令，用于消融实验；
   - `action_plan`：按 `instr_id` 从独立的 Planner JSONL 缓存读取 action
     plan，不修改原始 R2R annotation；
   - 零样本基线、GRPO 轨迹收集和训练后推理必须使用相同模式。当前
     零样本基线使用 `planner` 在线生成；正式 GRPO 训练与训练后主实验
     使用由同一固定 Planner 生成的 `action_plan` 缓存。两者交给导航
     Policy 的 action plan 文本完全一致。
   - 这里的 Planner 不是单指 `PLANNER_PROMPT` 字符串，而是“冻结的
     Qwen2.5-14B 基础模型（禁用策略 LoRA）+ `PLANNER_PROMPT` + 固定
     Chat Template 和解码参数”构成的完整规划器。
   - 正式 RL 训练前，用该 Planner 把 R2R 中每条原始 instruction 转成
     action plan，并按 `instr_id` 保存为派生 JSON/JSONL。这里的“离线
     缓存”不是重新下载 R2R，而是保存模型生成结果，避免每个 epoch 和
     同组 rollout 重复调用 Planner。
   - 同一任务在训练期间始终读取相同 action plan；策略 LoRA 只优化逐步
     导航决策，避免 Planner 随 LoRA 更新而改变，导致状态分布非平稳。

4. 跑通零样本基线 (Baseline)：

   - 不挂载任何 LoRA 权重，用原生 Qwen2.5-14B HF 模型在 R2R 验证集上
     跑通完整推理流程；
   - 记录 SR、SPL、平均轨迹长度、思考内容一致性等基线指标，作为后续对比基准。

   **当前状态：已完成。** HF Qwen2.5-14B-Instruct-1M 在
   `R2R_val_unseen_instr` 的 2349 条指令上得到：SR 22.26、SPL 14.38、
   oracle SR 37.85、nDTW 30.55、SDTW 14.49、CLS 31.35。该结果是后续
   LoRA/GRPO 实验的统一零样本基线。

### 阶段一补充：固定 Planner 离线缓存（当前步骤）

代码已实现，服务器尚需执行生成：

1. `nav_src/scripts/action_planner.py generate` 固定使用已验证的单卡 HF
   Qwen2.5-14B、`PLANNER_PROMPT`、tokenizer 原生 Chat Template、
   temperature=0、Transformers 4.48.3 和固定模型文件校验信息；
2. 14,039 条 `R2R_train_enc` instruction 按 `global_index % 4` 分为四个
   独立单卡任务，数量固定为 3510、3510、3510、3509；
3. 每生成一条就追加并 `fsync` 到 JSONL；重跑同一命令会校验 manifest、
   跳过已有 `instr_id`，并只修复可能存在的末尾半条 JSON；
4. `merge` 只接受四个完整且 Planner 指纹一致的分片，并校验恰好 14,039
   个唯一 `instr_id`、原始 instruction、全局顺序和分片归属；
5. `--navigation_input_mode action_plan --action_plan_cache ...` 会在数据加载
   阶段按 `instr_id` 挂载缓存，Policy 不再在线重复调用 Planner；
6. `verify-online` 会用同一 Planner 在线重算少量样本，要求其 action plan
   与缓存逐字符一致。服务器完整命令见 `docs/运行命令.md` 第 5 节。

## 阶段二：强化学习环境与奖励函数的构建

**目标：** 封装标准 Gymnasium 风格的 RL 环境，实现三类复合奖励的自动计算，为 GRPO 训练提供标准化数据接口。

### 第三步：封装标准强化学习环境包装器（Gymnasium 风格）

基于原项目 `nav_src/env.py` 扩展 RL 核心 Wrapper，并提供 TRL 环境
适配层：

1. **状态（State）生成**：打包「系统规则 + planner 生成的 action plan
   + 当前场景文本描述 + 历史轨迹总结」为完整 Prompt，与推理阶段完全
   一致；instruction 模式仅用于明确配置的消融。
2. **动作（Action）解析**：复用阶段一的统一解析器，接收完整
   `<Think>/<Action>` 文本，解析 Viewpoint ID、回溯或 `Finish!`。
3. **辅助信息输出**：保留当前节点坐标、已访问节点集合、视觉特征或
   原始图像、结构化 thought、动作合法性和各奖励分项。
4. **结束标志**：主动停止/成功或不可恢复异常属于 `terminated`；最大
   步数属于 `truncated`。只有“距离目标小于 3m 且主动输出 Finish!”
   才计算主动停止成功。
5. **TRL 适配**：环境的 `reset()` 从 R2R 任务行恢复同一起点，只公开
   `submit_navigation_decision()` 作为模型工具；`trl_environment_reward()`
   作为显式 `reward_funcs` 读取 episode 累积奖励。同一 GRPO group 必须
   使用同一 instruction、起点和初始朝向。TRL 0.29 不会自动调用环境的
   `get_reward()`，因此不能把奖励读取实现成第二个公开环境方法。

### 第四步：实现三类复合奖励函数

在`step()`中同步计算基础导航奖励、跨模态语义对齐奖励、思维质量奖励，加权求和后作为单步总奖励。

#### 4.1 基础导航奖励（核心骨架）

基于导航图几何信息计算，引导模型高效到达目标：

- 计算当前节点到目标节点的最短路径距离`dist = shortest_path_distance(current_node, target_node)`；
- 核心奖励项：
  - 路径效率奖励：若当前`dist` < 上一步`dist`，奖励 + 5；
  - 回头路惩罚：若当前节点在`visited_nodes`集合中，惩罚 - 10；
  - 无效动作惩罚：连续 3 步无有效位移，惩罚 - 20；
  - 指令偏离惩罚：未经过指令标注的关键地标节点，惩罚 - 50；
  - 最终成功奖励：距离目标 < 3m 且主动停止，奖励 + 100~+300；
  - 失败惩罚：提前停止、超时、环境异常，或被 TRL 的外部 token/tool-call
    上限提前截断，基础失败分项为 -80。为避免硬截断把同一 GRPO group
    中的大量早期失败轨迹全部压成 -80、进而产生全零优势，默认将剥离
    成功/失败终局分项后的稠密回报 `R_dense` 平滑映射为
    `R_fail=-80-20+20*tanh(R_dense/100)`。因此失败 episode return 始终
    小于 -80，同时仍单调保留有界的导航、CLIP 与思维奖励差异，既防止
    “前几步刷正奖励、最后失败”，也允许 GRPO 比较不同质量的失败探索。

#### 4.2 跨模态语义对齐奖励（新增创新点 1）

弥补视觉转文本的信息损失，引导模型向语义匹配的方向移动：

1. **准备原始视觉信号**：当前 NavGPT 主循环读取的是预生成文本 JSON，
   不包含 RGB。需先从 Matterport3D 视图离线预计算每个 viewpoint/朝向
   的 CLIP 图像特征，或启用渲染实时取图；不能用场景文本冒充视觉特征；
2. **预加载 CLIP 模型**：加载`clip-vit-large-patch14`，分别实现文本编码器与图像编码器；
3. **指令特征预计算**：训练前预先提取每条导航指令的 CLIP 文本特征，缓存备用；
4. **单步相似度计算**：每步执行动作后，读取与当前朝向对应的 CLIP 视觉特征，与指令文本特征计算余弦相似度；
5. **奖励计算**：定义状态势函数
   `Φ(s)=4·cos(CLIP(instruction), CLIP(rgb_s))`，单步语义奖励为
   `Φ(s_t)-Φ(s_{t-1})`；同时记录原始相似度和势函数值。该形式单步范围为
   `[-8,+8]`，闭合回路累计严格为零，避免逐步裁剪造成往返刷分。

#### 4.3 思维质量奖励（新增创新点 2）

约束思考过程的逻辑性与一致性，实现思考 - 动作协同优化：

1. **子目标对齐度**：用文本相似度模型计算思考内容与 action plan 的最大
   匹配度。由于当前生产数据没有版本化的“子目标文本 ↔ 真实 viewpoint”映射，
   该值只作诊断，奖励固定为 0，不能靠复述 plan 刷分；
2. **动作一致性**：只有已实际执行的移动/回退与思考中的唯一方向或 viewpoint
   精确一致，或 Finish 被环境确认成功时，才给原始 +5；泛化的 move、proceed、
   continue、含糊方向、未执行动作和未确认 Finish 均为 0，明确矛盾为 -8；
3. **事实一致性**：校验思考内容与当前场景描述、历史轨迹是否存在明确事实
   矛盾（如“前方有楼梯”但证据中没有楼梯），存在矛盾则原始惩罚 -8。整个
   Thought 族使用 `grounded_auxiliary_v1` 并统一乘 0.25，因此实际正奖为
   +1.25、矛盾惩罚为 -2。

#### 4.4 当前实现约束与落点

第四步由以下模块实现：

- `nav_src/navigation_rewards.py`：三类奖励的配置、逐项计算、按 rollout
  隔离的状态和稳定的奖励分项名称；
- `nav_src/clip_feature_cache.py`：指令 CLIP 特征、36 朝向原始视觉 CLIP
  特征的严格加载与校验，以及在线 thought 文本编码缓存；
- `nav_src/scripts/build_clip_cache.py`：从原始 Matterport3D RGB 视图构建
  可断点恢复的离线特征缓存；
- `nav_src/scripts/validate_rewards.py`：不加载 14B/CLIP 权重的确定性边界测试。

实现遵循以下数据契约：

1. `RewardResult.components` 才参与单步奖励求和；原始余弦相似度、阈值、
   连续无效步数等只写入 `diagnostics`，防止诊断值被误当奖励；
2. 语义奖励只接受原始 RGB 经过 CLIP vision tower 得到的特征。启用该
   奖励却缺少视觉缓存，或文本/视觉缓存的 model ID、revision、实际权重
   SHA256、特征维度不一致时立即报错；MatterSim 输出的 BGR 必须转换为
   RGB 后才能进入 CLIP；
3. R2R 原始 annotation 没有可靠的“关键地标节点/子目标节点”标注，因此
   这两项只读取可选 `reward_metadata.key_landmark_viewpoints` 和
   `reward_metadata.subgoal_viewpoints`，没有真标注时保持为零，不从路径或
   caption 伪造监督；
4. 事实一致性默认只惩罚 thought 中“楼梯在前方/可见”等明确且被当前
   场景文本、物体列表和历史轨迹否定的视觉断言。CLIP 文本相似度只作为
   grounding 诊断，低相似度本身不等于事实矛盾；也可注入独立 NLI/事实
   校验 scorer，并保持相同奖励接口；
5. 任何未实际执行的无效动作都不能获得子目标对齐或动作一致性正奖励；
6. 三大类均有独立 `enabled` 与 `weight` 配置，支持基础导航、加入语义、
   完整思维奖励三组消融，不需要修改环境状态机。

## 阶段三：强化学习微调代码的编写（LoRA + GRPO）

**目标：** 构建在线交互训练主循环，基于 TRL 库实现 GRPO 算法，仅更新 LoRA 参数，同步优化思考与动作输出。

### 第五步：设置 LoRA 适配器（PEFT）

基于 HuggingFace `peft`库为 LLM 注入可训练的 LoRA 适配器：

1. **参数配置**：`r=16`, `lora_alpha=32`, `lora_dropout=0.05`，目标模块覆盖`q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj`；
2. **冻结主干**：LLM 主干权重全部设置`requires_grad = False`，仅 LoRA 参数参与梯度更新，大幅降低显存占用，同时保留模型通用常识与泛化能力；
3. **权重初始化**：初始 LoRA 对主干输出的增量为零（通常 A 随机、
   B 为零，并非所有矩阵都为零），确保训练起点与零样本基线对齐。

第五步由以下模块实现：

- `nav_src/lora_policy.py`：只从本地 HF Safetensors 目录加载 Qwen
  tokenizer/causal LM，初始化或重载可训练的 PEFT LoRA，并返回后续 GRPO
  可复用的 `LoRAPolicyBundle`；`PolicyModelLoader.load(adapter_path=None)`
  是第六步新训练与断点续训共用的模型入口；
- `nav_src/scripts/validate_lora_policy.py contract`：不加载 torch、PEFT 或
  14B 权重的确定性契约测试；
- `nav_src/scripts/validate_lora_policy.py real`：在一张可见 GPU 上加载真实
  Qwen2.5-14B 并验证 LoRA 注入结果；
- `nav_src/scripts/validate_lora_policy.py full`：在短序列上完成基础模型与
  初始 LoRA logits 等价性、真实前向/反向、一次优化器更新、adapter 保存
  及重新加载后的 logits 等价性测试。

当前实现对前五项准备工作执行硬校验：模型必须是本地 `qwen2` HF
checkpoint；七类目标投影必须在每个 Transformer block 中各出现一次；
PEFT 实际替换的目标集合必须与注入前扫描结果一致；所有主干参数必须
冻结；可训练张量只能是每个目标层的一对 `lora_A/lora_B`，且其参数量
必须与目标矩阵形状推导出的理论值完全相等，可训练比例不得超过 1%。
完整生命周期测试还会逐个检查初始 `lora_A` 为非零随机值、`lora_B` 为零，
因此 LoRA 初始增量为零；反向传播后，冻结主干的梯度必须全部为 `None`，
所有可训练 LoRA 张量必须得到有限梯度。由于初始 B 为零，第一次反向时
`lora_A` 梯度可以为零，但必须至少有一个 `lora_B` 获得非零梯度，且
`optimizer.step()` 后其参数确实改变。

adapter 仅以 `adapter_model.safetensors` 和 `adapter_config.json` 保存，不复制
或覆盖 14B 基础权重；同时写入带基础模型配置、adapter 配置和权重 SHA256
的 `navgpt_adapter_manifest.json`。重载时会复核文件哈希、LoRA 超参数、目标
模块、冻结状态、理论参数量和本地 Qwen Safetensors 分片的联合 SHA256，
再对保存前后的 logits 做数值等价检查。基础模型权重指纹在每个进程首次
使用时计算一次，后续 checkpoint 复用，不会反复扫描 14B 权重。

### 第六步：基于 TRL 库集成 GRPO 算法

采用 TRL `GRPOTrainer` 的有状态环境接口实现在线 RL。三类奖励统一读取
同一个已执行的 `NavigationTransition`，避免环境奖励和文本奖励重复计分：

1. 轨迹收集（Rollout）：
   - `train_dataset` 提供 R2R 任务标识、原始 instruction、起点和初始朝向；
   - `environment_factory` 为每个 rollout 创建隔离的有状态导航环境；
   - 带 LoRA 的模型通过工具调用与环境多轮交互，逐步生成 Think 与
     Action，直至主动停止、失败或截断；
   - 环境内部记录每步状态、结构化输出、奖励分项和结束原因。
2. 奖励归一化与优势计算：
   - 基础导航、CLIP 和思维质量分项全部由环境逐步累积；显式注册
     `trl_environment_reward`，从各环境实例读取唯一的 episode 总奖励；
   - 不得再注册会重复计算格式、子目标、事实或动作一致性的 reward
     function；否则同一信号会被二次计分；
   - 按同起点 group 归一化 episode 总奖励，Think 与 Action token 共享
     优势信号，实现思考—动作协同优化。
3. 策略更新：
   - 采用 GRPO 标准损失函数，加入 KL 散度约束，避免策略偏离初始模型过远；
   - 仅更新 LoRA 参数，主干权重全程冻结。
4. 训练组件组装：
   - Dataset、固定 Planner 缓存、CLIP 特征、导航图、有状态环境和唯一复合
     reward function 在加载 Qwen 前完成来源与接口校验；
   - Trainer 创建前再次检查只有 `default` LoRA 的 A/B 参数可训练。
5. 首版 GRPO 配置：
   - 同时支持显式单卡和 `torchrun` DDP；统一保持
     `per_device_train_batch_size=1`、同一任务采样
     `num_generations=4`。单卡使用 `steps_per_generation=4`、梯度累积
     4 步；四卡 DDP 每个 rank 各生成一条 rollout，自动使用
     `steps_per_generation=1`、梯度累积 1 步；双卡对应 2/2。全局每个
     optimizer step 始终只包含一个完整的四 rollout GRPO group；
   - 使用 `learning_rate=1e-6`、cosine scheduler、3% warmup、
     `max_grad_norm=1.0`、`beta=0.001`、BF16 和标准 AdamW；
   - GRPO 训练态禁用基础模型及 LoRA Dropout，避免策略、旧策略和 reference
     对同一 token 的 logprob 因随机掩码不同而产生虚假的 ratio/KL；
   - `loss_type="grpo"`、`scale_rewards="group"`、单一复合奖励权重 1.0，
     不屏蔽环境截断失败样本；
   - `max_completion_length` 不猜默认值，必须在第 8 项用真实 Qwen
     tokenizer 完成 token 预算审计后显式填写；梯度累积必须在完整的 TRL
     generation buffer 边界结束，保证 checkpoint 不落在半组 rollout 中间。
6. 奖励与训练日志：
   - 保留 TRL 原生的 loss、learning rate、gradient norm、KL、entropy、
     completion 长度、tool call 和 group reward 指标；
   - `logs/train_metrics.jsonl` 按 Trainer log step 同步写入 episode return、
     SR、oracle SR、截断率、协议违规率、平均步数、最终/最小距离和三类奖励
     的每个分项均值；
   - `logs/navigation_rollouts.jsonl` 为每条 rollout 写入任务 ID、结束原因、
     轨迹 viewpoint、奖励分项和协议违规；每 10 个 group 额外保存一次紧凑
     Think/Action 逐步轨迹供人工检查奖励黑客，不重复保存完整 prompt 和场景
     文本。断点续训后 rollout/group 序号继续递增。
   - 每次新启动或续训同时写入 `training_sessions.jsonl`；若进程在最近一次
     checkpoint 后才崩溃，旧的未恢复 rollout 仍保留但属于前一 session，
     不会与恢复分支静默混为一条曲线。
   - DDP 下每个 rank 只持有本地环境和 rollout；所有 rank 在奖励边界用
     collective 汇总紧凑轨迹，只有 global rank 0 分配全局 rollout/group
     编号并写 JSONL，避免并发追加导致重复、乱序或文件损坏；
7. Checkpoint 与断点续训：
   - 沿用 Transformers Trainer 的 `checkpoint-N`，保存 `default`/`ref`
     LoRA、optimizer、scheduler、每个 DDP rank 的 RNG、`trainer_state.json`
     和 tokenizer；FP16
     路径还必须保存 `scaler.pt`；不保存 Qwen 14B 基座权重；
   - 每个 checkpoint 额外写入 adapter 来源清单、不可变 run manifest 和包含
     文件大小/SHA256 的恢复清单；缺文件、哈希改变、步数不一致、基础模型
     权重混入，或 Qwen 分片权重、核心实现代码、数据、tokenizer、
     奖励/LoRA/GRPO 配置变化时均拒绝续训；
   - 续训先从 checkpoint 根目录加载可训练 `default` adapter，TRL 再建立
     reference adapter，随后由 `trainer.train(resume_from_checkpoint=...)`
     恢复 `ref`、优化器、调度器、随机数和 Trainer 步数；训练结束另存
     `final-adapter-step-N`。
   - DDP 续训以 checkpoint 清单中的 LoRA SHA256 为唯一真值：训练器恢复前
     及其内部恢复完成后各校验一次 `default` adapter；若 worker rank 仍是
     初始权重，则从 rank 0 逐个小 LoRA 张量同步并重新验哈希，而不重新启用
     会触发当前 Blackwell/NCCL 问题的大聚合初始化广播。`ref` adapter 也在
     第一条续训轨迹生成前从 rank 0 逐张量同步，保证各 rank 使用同一 KL
     参照策略。冻结的 Qwen 14B 主干始终不参与这些广播。
   - 若上述恢复修复应用于修复前已生成的 checkpoint，必须显式提供补丁原因。
     系统仅接受实现代码摘要这一项变化，仍逐项拒绝模型、数据、奖励、优化参数
     或 DDP 拓扑变化；旧 run fingerprint 保持不变，旧/新实现摘要、恢复步数和
     原因写入独立补丁账本，并随新 checkpoint 与最终 adapter 一同保存。
   - checkpoint 和最终 adapter 保存前对所有 rank 的可训练 LoRA 张量计算
     逐字节 SHA256；任何 rank 参数不一致都会立即终止，不生成可恢复清单。
8. 分四级验证：
   - 在正式训练前依次进行依赖与配置契约、真实组件、真实 14B Trainer
     构造/单组 rollout、短训练与断点等价性验证；本项单独实施，不由前述
     代码或轻量测试替代。
   - `scripts/validate_grpo_levels.py` 以 `level1`—`level4` 四个独立入口实现
     逐级放行。Level 2 使用真实 Qwen tokenizer 遍历 14,039 个初始任务和
     61 个 scan 的全部有向可达 viewpoint 朝向，审计初始 prompt、工具返回
     后缀和多轮工具 transcript，并输出正式训练唯一允许使用的
     `recommended_max_completion_length`；部分抽样报告不能放行 Level 3。
   - Level 3 加载 Qwen2.5-14B 与 LoRA，调用固定 TRL 0.29.1 的真实单组生成/
     评分边界，要求四条 rollout 属于同一任务、至少执行一次导航工具、奖励
     全部 finalization，并产生有限且组内居中的 advantage 和 reference
     log-probability。
   - Level 4 在三个独立进程中执行连续 2 step、训练 1 step 后停止、从
     `checkpoint-1` 恢复至 step 2；逐张量比较最终 LoRA，并比较 optimizer、
     scheduler、RNG、Trainer 步数及八条 rollout。任何差异都会阻止正式训练。
   - 当前 Qwen2.5 tokenizer 的工具 XML 与 TRL 内置 Qwen3 schema 兼容，但
     TRL 0.29.1 不会自动识别该模板；Trainer 构造前显式安装经过解析测试的
     response schema，避免工具调用被当作普通文本。
   - DDP 另运行真实四卡验证：连续训练 2 step，再从复制到独立分支的
     `checkpoint-1` 恢复到 step 2，逐张量比较最终 LoRA，并比较 optimizer、
     scheduler、四份 rank RNG 与八条 rollout；单卡验证不能替代本项。

## 阶段四：训练与验证

**目标：** 完成迭代训练，通过多组对比与消融实验验证各创新点的有效性，形成完整的论文实验支撑。

### 第七步：在线交互与迭代训练

1. **训练主循环**：执行「采样指令→环境交互收集轨迹→GRPO 更新 LoRA」的闭环迭代，实时监控平均奖励、成功率、平均步数等指标的变化趋势。
2. 奖励黑客防范：
   - 定期人工抽检轨迹的思考内容，避免模型生成无意义长思考来骗取奖励；
   - 根据训练曲线动态调整各类奖励的权重，如发现模型原地规避惩罚，则加重最终成功奖励的权重。
3. **Checkpoint 保存**：每训练固定数量的 Episode，保存一次 LoRA 权重，并在验证集上快速测评，保留最优权重。

### 第八步：论文核心实验设计（适配 ICRA/ACM MM 等会议要求）

基于测试集（Val-Unseen / Test）完成以下实验，全面验证方案有效性：

#### 8.1 主对比实验（Main Results）

验证方案的整体性能提升：

- 对比组 1：NavGPT (GPT-3.5 零样本) vs Ours (14B 本地 + 完整 RL 方案)

  核心叙事：开源本地模型经 RL 微调后，性能比肩或超越闭源模型零样本效果

- 对比组 2：本地 14B 模型零样本 vs Ours (14B 本地 + 完整 RL 方案)

  核心叙事：强化学习为零样本 LLM 带来了导航规划能力的质变提升

- 对比组 3：同量级端到端 VLN 模型（如 NaviLLM） vs Ours

  补充说明模块化方案与端到端方案的性能差距与泛化性优势

#### 8.2 消融实验（Ablation Study）

逐层验证每个创新组件的贡献，对应三层创新点：

| 实验组                 | 基础导航奖励 | 语义对齐奖励 | 思维质量奖励 | 核心观测指标                   |
| ---------------------- | ------------ | ------------ | ------------ | ------------------------------ |
| 基线（零样本）         | ✗            | ✗            | ✗            | SR / SPL / 平均步数            |
| 仅基础 RL              | ✓            | ✗            | ✗            | SR / SPL / 回头路占比          |
| + 语义对齐奖励         | ✓            | ✓            | ✗            | SR / 指令语义匹配度            |
| 完整方案（+ 思维奖励） | ✓            | ✓            | ✓            | SR / 动作一致性 / 可解释性评分 |

- 额外消融：GRPO 与 传统 PPO 的训练效率、稳定性对比；LoRA 秩 (r) 对最终性能的影响。

#### 8.3 定性分析（Qualitative Results）

1. **轨迹可视化对比**：选取长指令典型 Case，对比零样本模型与 Ours 的行走轨迹，直观展示 RL 对回头路、绕路问题的改善效果。
2. **思考过程对比**：展示同一场景下，零样本模型与 RL 训练后模型的思考内容差异，体现训练后推理更有条理、子目标拆解更清晰、事实矛盾更少。
3. **失败案例分析**：分析剩余失败场景的原因，明确当前方案的能力边界与未来优化方向。
