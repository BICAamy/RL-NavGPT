# NavGPT LoRA-GRPO 训练流程与概念讲解

本文档解释当前项目中“Qwen2.5-14B + LoRA + GRPO + 三类复合奖励”的
训练过程、单卡/多卡关系、关键术语、输出文件和训练后测试边界。实际可复制
命令见 [`docs/训练命令.md`](训练命令.md)。

## 1. 当前处于什么阶段

阶段六已经完成以下真实验证：

- 真实 Qwen2.5-14B、CLIP、R2R 环境和四条同任务 rollout 可以组装；
- 单卡连续训练与 checkpoint 恢复逐张量一致；
- 四卡 DDP 连续训练与 checkpoint 恢复逐张量一致；
- 当前服务器使用 `blackwell-safe` NCCL profile 时，LoRA 梯度同步稳定；
- 正式训练唯一允许使用的 `MAX_COMPLETION_LENGTH` 已由 Level 2 全量审计得到，
  当前报告值为 `38912`。

因此现在可以开始 8.1 中 Ours 模型的正式训练。但“完成 8.1 主对比实验”还
包括训练后的统一推理和 R2R 指标评测。当前 `scripts/train_grpo.py` 已经能训练
和保存 adapter；统一 Policy 接口会校验 adapter manifest、基础模型
指纹、LoRA 配置和目标层覆盖，加载后基础模型与 LoRA 全部冻结并
进入 `eval()`。固定 Val-Unseen-128 快评、完整 Val-Unseen 评测和 best
checkpoint 管理也已接入训练入口。

固定 `max_steps` 的验证生命周期同样纳入正式协议：最终 optimizer step 会先
强制形成可恢复 checkpoint；正常 `train_end` 再对“最终 checkpoint + 当前
quick-best”执行完整 Val-Unseen 并更新 `full_best`。若该 step 已完成 epoch-end
full，则复用同一个不可变事件，避免重复评测和重复选择。

Base Qwen 和 RL LoRA 的论文级结果只允许由
`nav_src/scripts/evaluate_r2r_native.py` 产生，它与训练期评测共用 native tool
transcript。`NavGPT.py` 只保留为历史 LangChain/OpenAI 系统复现入口，
其 manifest 固定标记 `official_rl_comparable=false`。训练日志中的
success rate 仍不能当成 Val-Unseen 测试结果；训练期评测读取
`validation/evaluations/*/metrics.json`，最终 Base/LoRA 对比读取独立 native
evaluator 输出。

## 2. 这次训练到底在优化什么

整体数据流如下：

```text
R2R train instruction
        │
        ├── 固定 Planner 的离线 action plan（只读）
        ├── 预生成场景文本/物体/可导航节点（只读）
        └── 原始视觉 CLIP 缓存（只读，仅用于奖励）
                         │
                         ▼
冻结的 Qwen2.5-14B + 可训练 LoRA
                         │
              生成 Think + 导航工具动作
                         │
                         ▼
R2R 环境执行动作，形成一条 rollout/episode
                         │
                         ▼
基础导航奖励 + 视觉语义奖励 + 思维一致性奖励
                         │
                         ▼
同一任务 4 条 rollout 组内比较（GRPO）
                         │
                         ▼
只反向更新 LoRA A/B 参数，Qwen 主干保持冻结
```

训练中会改变的只有决策模型中的 LoRA 参数。以下内容不会训练：

- Qwen2.5-14B 基础权重；
- 固定 Planner 及已经生成的 action plan；
- CLIP 文本塔和视觉特征缓存；
- Matterport/R2R 图结构、场景文本和物体描述；
- 奖励函数本身。

这意味着最终保存的不是另一份完整 14B 模型，而是体积小得多的 LoRA adapter。
推理时需要“同一份 Qwen 基础模型 + 训练后的 adapter”共同工作。

## 3. 一次全局训练 step 内部发生了什么

四卡正式配置下，一次 `global_step` 包含以下过程。

1. 数据采样器选出一条 R2R 训练任务，例如某个 `instr_id`。
2. 该任务被重复 4 次，分别发送给 rank 0、1、2、3；四个进程看到相同的
   instruction、action plan 和初始导航状态。
3. 每个 rank 使用当前 LoRA 策略独立采样一条完整 rollout。rollout 最多执行
   10 次导航工具调用；每次动作后环境返回新的观察，模型可以继续思考和行动。
4. 每条 rollout 结束时，环境汇总基础导航、跨模态语义和思维质量三类奖励，
   得到一个 episode return。
5. GRPO 在这 4 个 return 内计算组内相对 advantage。高于组平均的轨迹获得
   正 advantage，低于组平均的轨迹获得负 advantage。
6. TRL 同时计算策略 log-probability 和 reference policy log-probability，
   用 `beta` 控制 KL 约束，防止 LoRA 策略一次更新偏离初始模型过远。
7. 每张卡只对本地 rollout 做前向和反向；DDP 使用 NCCL 对所有 LoRA 梯度
   做 AllReduce，四个 rank 得到完全一致的聚合梯度。
8. AdamW 对 LoRA 参数执行一次 optimizer step，scheduler 更新一次学习率，
   `global_step` 增加 1。
9. 按配置写训练指标、rollout 记录和 checkpoint。

简化后的组内 advantage 可以理解为：

```text
A_i = (R_i - mean(R_group)) / (std(R_group) + epsilon)
```

项目把三类奖励先合并为唯一的 episode reward，再交给 TRL 做一次组内归一化，
不会把三类奖励错误地当成三个独立 reward model 再分别归一化。

## 4. LoRA 与 LoRA tensor 是什么

### 4.1 Tensor

Tensor（张量）就是存储模型数值的多维数组。标量是 0 维 tensor，向量是 1 维，
矩阵是 2 维；神经网络权重通常是二维或更高维 tensor。

### 4.2 LoRA

对基础模型中的一个冻结权重矩阵 `W`，LoRA 不直接修改 `W`，而是学习两个
低秩矩阵 `A` 和 `B`：

```text
W_effective = W + (alpha / r) * B @ A
```

- `W`：Qwen 原始权重，`requires_grad=False`；
- `A`、`B`：LoRA tensor，`requires_grad=True`；
- `r`：低秩维度，当前为 16；
- `alpha`：LoRA 更新的缩放系数，当前为 32；
- `B @ A`：LoRA 学到的任务增量。

“梯度只进入 LoRA”表示反向传播后只有 A/B tensor 拥有并更新梯度，Qwen 主干
不会变化。`adapter_model.safetensors` 保存的主要就是这些 LoRA tensor。

项目 checkpoint 还会计算全部可训练 LoRA tensor 的 SHA256。DDP 中四个 rank
的 SHA256 必须一致，否则 checkpoint 会被判为不可安全恢复。

## 5. GRPO 中最容易混淆的几个数量

### 5.1 `num_generations`

对同一个任务采样多少条候选 rollout。当前为 4。GRPO 必须有同任务的多个
候选，才能比较“哪条相对更好”。它不是 GPU 数量，也不是导航步数。

### 5.2 `per_device_train_batch_size`

每个进程单个微批次包含多少条样本。当前实现固定为 1，不能通过命令修改。

### 5.3 `world_size`

参与 DDP 的进程/GPU 数量。单卡为 1，双卡为 2，四卡为 4。

### 5.4 `steps_per_generation`

TRL 在每个 rank 上为组成一次完整 generation buffer 需要处理的本地微批次数。
本项目首版 DDP 为保证“每个 buffer 恰好一个完整 GRPO group”，强制：

```text
steps_per_generation = num_generations / world_size
```

### 5.5 `gradient_accumulation_steps`

每个 rank 累积多少个本地微批次的梯度后，才执行一次 optimizer step。本项目
同样强制：

```text
gradient_accumulation_steps = num_generations / world_size
```

这里的累积是为了让同一个 optimizer step 覆盖完整的四条 rollout，不是为了
人为扩大到多个 GRPO group。

### 5.6 三种拓扑的对应关系

在 `num_generations=4`、每卡 batch size 为 1 时：

| 模式 | world size | 每卡获得的 rollout | steps_per_generation | gradient_accumulation_steps | 每个 global step 的全局 rollout |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单卡 | 1 | 4 | 4 | 4 | 4 |
| 双卡 | 2 | 2 | 2 | 2 | 4 |
| 四卡 | 4 | 1 | 1 | 1 | 4 |

因此单卡与多卡在算法语义上相同：都是“同一任务 4 条 rollout → 一次 LoRA
更新”。区别是单卡串行生成 4 条，四卡各生成 1 条并行处理，然后同步梯度。

当前 `num_generations=4` 只能搭配 1、2、4 张卡。3 张卡无法整除 4，会在加载
模型前被拒绝。不要手动填写 `steps_per_generation` 或
`gradient_accumulation_steps`；让训练入口按 GPU 数量自动推导。

## 6. Episode、rollout、导航 step、global step 和 epoch

| 名称 | 在本项目中的含义 |
| --- | --- |
| task/sample | 一条带唯一 `instr_id` 的 R2R instruction |
| rollout/episode | 模型从起点开始交互，直到 Finish、成功、失败或截断的一整条轨迹 |
| navigation step | rollout 内的一次策略决策和环境动作 |
| tool call | 模型调用一次导航工具；通常对应一次导航决策，但协议错误也会被计数 |
| microstep | 单个 rank 对一个本地 batch 的前向/反向 |
| global/optimizer step | 聚合完整 GRPO group 后更新一次 LoRA |
| epoch | 训练采样器完整遍历训练集一次 |

当前 R2R 训练集有 14,039 条 instruction。在默认“一条任务对应一个 GRPO
group”的配置下，1 epoch 大约是：

```text
14,039 个 global steps
56,156 条 rollout（14,039 × 4）
最多 561,560 次导航工具交互（再乘 max_navigation_steps=10）
```

实际 rollout 可能提前 Finish，因此“最多”不等于实际数量。这也解释了为什么
完整一轮会很慢：四卡加速的是同一 group 内的四条 rollout，不会把一个 epoch
的任务数除以 4。

`trainer_max_steps > 0` 会覆盖 epoch 设置；`trainer_max_steps=-1` 才会使用
`num_train_epochs`。正式一轮训练采用 `-1 + 1.0 epoch`，此前 1/2/10-step
均只是验证，不是可用于论文的最终模型。

## 7. 三类复合奖励如何进入训练

单步奖励由以下三族组成，episode return 是整条轨迹的累计值并经过失败边界
整形：

1. `navigation/*`：进度、重访、连续无效动作、成功、失败和失败整形；保留
   `landmark_deviation`、`subgoal_completion` 两个稳定日志字段但值强制为 0，
   因为 `disabled_no_grounded_annotations_v1` 明确禁止无真标注的 metadata
   奖励；
2. `semantic/*`：使用 `bounded_raw_visual_potential_v1`，计算当前原始视觉
   CLIP 特征相对 instruction 的端点势能变化。scale、weight 和安全比例写入
   run manifest；理论整段绝对值不得超过成功终局奖励的 25%；
3. `thought/*`：使用 `grounded_auxiliary_v1`。文本与 action plan 的子目标相似度
   只记录诊断、奖励恒为 0；只有已执行动作与唯一方向/viewpoint 精确一致，或
   环境确认成功 Finish，才产生原始 +5。明确矛盾、解析错误和无效动作产生原始
   -8，整个 Thought 族统一乘 `0.25`；泛化的 move/proceed/continue 不给正分。

策略输入仍是 action plan、场景文本和轨迹历史。CLIP 原始视觉特征只参与奖励，
不会在推理时偷偷作为额外输入喂给 Qwen。这一点保证创新点是“用视觉信号监督
文本决策策略”，而不是把模型改造成另一个视觉编码器。

训练 prompt 会包含固定 Planner 生成并缓存的 action plan，但不包含
ground-truth path 或 goal viewpoint。HF Dataset 只保存 action plan 的摘要，
环境按 `instr_id` 取回对应缓存；环境内部可以读取目标和最短距离来计算奖励，
但这些监督信息不会泄漏到策略输入。

R2R 的参考 path 不等于子目标/地标标注。把中间 path 节点直接当子目标会奖励
模仿单条示范路线并惩罚合法替代路径，因此当前不生成 `reward_metadata`。源数据
可用性由 `audit_reward_metadata_sources.py` 审计，协议身份和两项零配置进入
immutable run manifest，rollout audit 还会验证它们从未非零。

其中 navigation progress 使用固定版本 `distance_potential_v1`：

```text
progress = 5.0 × (previous_distance - current_distance)
```

它只作用于真实执行的移动，不做只保留正值的阈值或裁剪。靠近目标得到连续正
奖励，走远得到对称负奖励；整条轨迹的 progress 和严格化简为
`5.0 × (start_distance - final_distance)`，因此不能通过先靠近再走远反复刷分。
算法版本和 scale 都写入不可变 run manifest。

## 8. 正式训练参数及作用

| 参数 | 正式值 | 含义与影响 |
| --- | ---: | --- |
| `max_completion_length` | Level 2 当前为 38912 | 整段多轮 completion/transcript 的 token 安全上限，不代表每条必然生成这么长 |
| `max_navigation_steps` | 10 | 单条 episode 最多执行的导航决策数 |
| `navigation_progress_scale` | 5.0 | shortest-path distance potential 的缩放；每米净靠近对应 +5，走远对应负值 |
| `semantic_potential_scale` | 4.0（source） | 原始视觉 CLIP endpoint potential 的缩放；第五阶段先扫描 0/4/8/12/16/20/24，再确定 smoke 候选，硬上限为 25 |
| `thought_reward_weight` | 0.25 | 保守 Thought 辅助权重；有效正奖为 +1.25、矛盾惩罚为 -2，文本子目标对齐为 0 |
| `max_tool_calling_iterations` | 10 | TRL 多轮工具调用上限，应与环境导航上限一致 |
| `num_generations` | 4 | 每个任务的同组候选 rollout 数 |
| `learning_rate` | 1e-6 | AdamW 更新 LoRA 的步长；过大可能破坏策略，过小学习很慢 |
| `weight_decay` | 0 | LoRA 参数不额外施加权重衰减 |
| `warmup_ratio` | 0.03 | 前 3% global steps 从低学习率升到目标学习率 |
| `lr_scheduler_type` | cosine | warmup 后按余弦曲线衰减学习率 |
| `max_grad_norm` | 1.0 | 梯度裁剪阈值，抑制异常大更新 |
| `beta` | 0.001 | reference KL 约束强度；越大越保守 |
| `temperature` | 1.0 | rollout 探索随机性；训练时需要候选差异 |
| `top_p` | 0.95 | nucleus sampling 截断范围 |
| `dtype` | bf16 | 模型计算精度；Blackwell 支持，范围通常比 fp16 稳定 |
| `r/alpha` | 16/32 | LoRA 容量与更新缩放 |
| `lora_dropout` | 0.05（adapter 配置） | GRPO Trainer 会统一禁用训练期 dropout，保证 policy/old/reference logprob 可比 |
| `save_steps` | 50 | 每 50 次 optimizer 更新保存 checkpoint |
| `save_total_limit` | 3 | 只保留最近 3 个标准 checkpoint，控制磁盘占用 |
| `trajectory_log_interval` | 10 | 每 10 个 GRPO group 保存一次详细逐步轨迹；每条 rollout 摘要仍会保存 |
| `seed` | 0 | 数据顺序、初始化和采样的随机种子 |

正式训练不使用 `--full-determinism`。该开关用于连续/续训逐字节审计，会牺牲
速度；正式训练仍保存完整 RNG 状态，并应通过多个随机种子报告论文结果。

## 9. 训练日志应该怎么看

输出目录中最重要的文件：

```text
OUTPUT_DIR/
├── navgpt_grpo_run_manifest.json     # 不可变训练配置、数据和代码摘要
├── logs/
│   ├── train_metrics.jsonl           # 每次 logging 的聚合指标
│   ├── navigation_rollouts.jsonl     # 每条 rollout 的奖励与导航摘要
│   └── training_sessions.jsonl       # 首次训练/每次续训会话
├── checkpoint-N/                     # 可精确续训状态
└── final-adapter-step-N/             # 训练结束后的部署/评测 adapter
```

优先观察：

- `nav/success_rate`：训练 rollout 中显式 Finish 且成功的比例；
- `nav/oracle_success_rate`：轨迹是否曾进入成功区域，即使最后没有正确 Finish；
- `nav/episode_return_mean/std`：平均复合回报及组内差异；
- `nav/final_distance_mean`：结束时到目标的平均距离；
- `nav/mean_steps`、`nav/mean_tool_calls`：轨迹长度；
- `nav/protocol_violation_rate`：输出格式/工具协议错误率；
- `nav/reward_family/navigation|semantic|thought`：三类奖励趋势；
- `grad_norm`、`learning_rate`、`loss`、`kl`：优化稳定性。

GRPO 的 loss 不是监督学习交叉熵，可能非常小、接近 0，甚至短时为负。仅凭
`train_loss` 不能判断是否学习；需要结合 LoRA hash 是否改变、reward/SR/KL
趋势和独立验证集指标。

训练 SR 也不是论文 SR：它来自正在用于优化的 R2R train rollout，包含探索
采样。论文结果必须来自冻结 adapter 后的 Val-Unseen/Test 推理。

## 10. Checkpoint 与 final adapter 的区别

`checkpoint-N` 用于继续训练，除 LoRA 外还包含 optimizer、scheduler、每个
rank 的 RNG、Trainer 状态、reference adapter 和完整 manifest。续训必须指向
原输出目录内的完整 `checkpoint-N`。

`final-adapter-step-N` 用于推理或评测，只包含部署需要的 adapter 权重、配置和
来源校验。它不能替代完整 checkpoint 继续训练。

以下做法都是错误的：

- 只拿 `adapter_model.safetensors` 续训；
- 把 checkpoint 复制到另一个输出目录再续训；
- 续训时改变 GPU 数量、学习率、数据路径或奖励配置；
- 训练中途修改被 run manifest 纳入摘要的实现文件。

## 11. 单卡和多卡流程是否一样

算法层面相同，工程层面不同。

相同点：

- 同一个基础模型、LoRA、数据、环境和三类奖励；
- 每组都是 4 条同任务 rollout；
- 每个 global step 都只更新一次 LoRA；
- checkpoint 和最终 adapter 格式相同。

不同点：

- 单卡串行处理四条 rollout；四卡并行各处理一条；
- 多卡每个 GPU 有独立进程和完整冻结 Qwen 副本，不是把 14B 权重切成四份；
- 多卡需要 NCCL 同步 LoRA 梯度和必要的对象数据；
- 当前服务器多卡必须使用 `blackwell-safe` transport；
- DDP checkpoint 保存四份 rank RNG，恢复时 world size 必须不变。

所以四卡的主要收益是把同组四条生成并行化，而不是将单条生成加速四倍。

## 12. 训练与测试的完整论文流程

### 12.1 训练阶段

1. 只使用 `R2R_train_enc.json`、训练 action-plan cache 和训练 CLIP cache；
2. 从相同 Qwen2.5-14B 基础权重初始化 LoRA；
3. 四卡在线采样、计算完整复合奖励并更新 LoRA；正式命令运行 2 epochs；
4. 每到 1000、2000、3000……optimizer step，先保存不可变 snapshot，再在固定
   Val-Unseen-128 上快评并刷新全局 quick-best；
5. 每个 epoch 结束，分别在完整 Val-Unseen 上评测当前 epoch-end 和全局
   quick-best；selector 再与历史 full-best 比较，按 SPL 优先更新 full-best；
6. 如果训练由正数 `max_steps` 正常结束，强制保存最终 checkpoint，并在
   train-end 对最终 checkpoint 与 quick-best 做一次完整评测；与 epoch-end
   重合时复用同一步 full event；
7. 保存日志、checkpoint 和最终 adapter；训练过程中完全不访问 Test 标签。

对 2-epoch run，可以把时间线理解为：

```text
epoch 1: train → 每 1000 step 快评 → epoch-end 全评 → full-best #1
epoch 2: train → 每 1000 step 快评 → epoch-end 全评 → full-best #2
最终冻结 validation/state.json 中的 full_best.adapter_path
→ 只用该 adapter 运行最终 Val-Unseen / Test
```

如果训练或评测进程中断，`checkpoint-N`、eval snapshot、queue JSON 和分 rank
JSONL 共同构成恢复点。正常续训会先补完 queued/running 评测，再执行下一个
optimizer step；`--validation-only` 可只补评测并退出，用于故障诊断和闭环验收。

### 12.2 模型选择与调参阶段

应事先固定一个验证协议，评估若干 checkpoint 或最终 adapter。任何学习率、
奖励权重、训练步数选择都只能依据开发/验证协议，不能依据 R2R Test 标签。
若反复观察 Val-Unseen 并据此调参，需要在论文中如实说明。

### 12.3 8.1 对比组 1

同一 Qwen Base vs Base+LoRA 的直接 RL 对比至少固定以下条件：

- 相同 R2R split 和完整样本数（`--iters -1`）；
- 相同场景文本、object、navigable/connectivity 数据；
- 相同最大导航步数和成功阈值；
- 相同指标实现：SR、SPL、NE、OSR、nDTW、SDTW、CLS；
- 固定随机种子并保存所有预测轨迹；
- Ours 推理时冻结 LoRA，不运行奖励、不反向传播、不再更新参数。
- Base 与 LoRA 都使用 native tool transcript，tool decision 生成上限固定为
  256 tokens，并核对 protocol fingerprint 一致。

“NavGPT GPT-3.5 原始系统 vs Ours”属于系统级主对比，因为两者 Planner/策略
模型并不完全相同。还必须保留 8.1 对比组 2“同一 Qwen2.5-14B 零样本 vs
同一基础模型 + RL LoRA”，它才直接隔离 RL 带来的增益。
GPT-3.5 可以继续用 `NavGPT.py` 复现，但必须作为
`legacy_langchain` 系统级参考单独报告，不得伪装成 native 协议可比
结果。

### 12.4 多随机种子

单个 seed 可以先得到首个主模型，但论文主结果最好至少运行 3 个训练 seed，
报告均值和标准差。不同 seed 必须使用不同输出目录；除 `--seed` 外其余配置、
数据和评测协议保持不变。

## 13. 训练后的正式评测边界

训练期 checkpoint 选择与四卡中断恢复闭环已经完成：每 1000 step 在固定
Val-Unseen-128 上刷新 quick-best；每个 epoch 结束后对全局 quick-best 和
epoch-end 做完整 Val-Unseen，并保留历史 full-best，最终以完整集 SPL 为主指标
选择。候选在
Trainer 清理旧 checkpoint 前先固化为不可变 LoRA eval snapshot；持久化队列
负责中断续跑，selector 只消费已完成 job 的标准 R2R 指标。

训练后的正式 Base/LoRA 对比使用唯一入口
`nav_src/scripts/evaluate_r2r_native.py`：

1. 当前历史 run 使用经过 provenance 校验的不可变 step-375/step-750
   snapshot 显式评测；只有新协议训练且 full validation 已携带同一
   256-token/2349-item protocol 的未来 run，才允许直接解析
   `validation/state.json` 中的 `full_best.adapter_path`；
2. 同一 Qwen2.5-14B 不挂 LoRA，作为“RL 增益”直接对照；
3. 两组使用相同完整 Val-Unseen split、action plan、prompt、native
   transport、导航/tool 步数、256-token 上限、seed 与指标脚本；
4. 汇总 SR、SPL、NE、OSR、nDTW、SDTW、CLS 和逐条轨迹；
5. NavGPT GPT-3.5 只作为原论文 `legacy_langchain` 系统级对照。

可复制的 Base/LoRA 命令见 [`docs/训练命令.md`](训练命令.md)第 12 节。
历史 `max_new_tokens=512` 输出属于旧协议，不能与当前固定 256-token
协议直接对比。
