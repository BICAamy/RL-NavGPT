# NavGPT 推理运行命令

三个后端共享同一套导航 Prompt 和输出协议：

```text
<Think>基于指令、场景和历史的简洁推理</Think>
<Action>action_maker("32位viewpoint_id")</Action>
```

到达终点时：

```text
<Think>已经满足终点描述，可以停止</Think>
<Action>Finish!</Action>
```

命令行默认仍是 `planner`：先让当前后端模型把原始 instruction 拆分为
action plan，再把 action plan 交给逐步导航策略，用于在线基线与调试。
正式 GRPO 训练及训练后主实验使用 `action_plan` 加独立 JSONL 缓存；
`instruction` 保留为消融模式。

## 1. GGUF / llama.cpp（当前 Mac 调试模型）

```bash
cd nav_src

python3 NavGPT.py \
  --llm_backend gguf \
  --llm_model_name qwen2.5-14b-instruct \
  --local_model_path /Users/bigcat/Documents/MyCode/NavGPT/models/Qwen2.5-14B-Instruct-1M-Q4_K_M.gguf \
  --local_chat_template qwen \
  --navigation_input_mode planner \
  --output_dir ../datasets/R2R/exprs/qwen2.5-14b-gguf-planner \
  --temperature 0 \
  --max_new_tokens 256 \
  --gguf_n_ctx 4096 \
  --gguf_n_gpu_layers 48 \
  --iters 2
```

`qwen` 会让 GGUF 后端使用 ChatML；如果 GGUF 自带且能被
`llama.cpp` 正确识别聊天模板，可以使用 `--local_chat_template auto`。

## 2. Hugging Face 模型（14B 训练/基线权重）

HF 后端会调用 tokenizer 自带的 `apply_chat_template()`，不会手写
Qwen 特殊 token。以下目录中应包含 8 份 `.safetensors` 权重分片：

```bash
cd nav_src

python3 NavGPT.py \
  --llm_backend hf \
  --llm_model_name qwen2.5-14b-instruct-1m \
  --local_model_path ../models/Qwen2.5-14B-Instruct-1M \
  --local_chat_template auto \
  --local_dtype bf16 \
  --hf_device_map single \
  --navigation_input_mode planner \
  --output_dir ../datasets/R2R/exprs/qwen2.5-14b-hf-planner \
  --temperature 0 \
  --max_new_tokens 256 \
  --iters 2
```

`plain` 只应用于明确要求原始 completion prompt 的本地模型。
14B BF16 权重自身约 29.6GB，当前 16GB Apple Silicon 机器不适合直接
加载或训练该 HF 模型；本机继续使用 GGUF 做推理调试，HF 目录用于后续
拷贝到训练服务器或在足够显存/内存的机器上运行。

## 3. OpenAI 在线模型

先在项目根目录的 `.env` 中配置 `OPENAI_API_KEY`，然后运行：

```bash
cd nav_src

python3 NavGPT.py \
  --llm_backend openai \
  --llm_model_name gpt-3.5-turbo \
  --navigation_input_mode planner \
  --output_dir ../datasets/R2R/exprs/openai-planner \
  --temperature 0 \
  --iters 2
```

在线后端直接接收中性的导航 Prompt，不会被套入 Qwen ChatML。

## 4. 完整零样本基线

确认 2 条样例能够稳定输出合法 Think/Action 后，将独立实验目录中的
`--iters` 改为 `-1`，即可遍历完整 split：

```bash
python3 NavGPT.py \
  ... \
  --val_env_name R2R_val_unseen_instr \
  --iters -1
```

## 6. 第三步：验证 Gymnasium / TRL 强化学习环境包装器

第三步不加载 14B 模型，也不占用 GPU；它使用真实 R2R annotation、场景
文本、导航图和第 5 节生成的 action plan 缓存，逐项检查环境状态机。

### 6.1 建立独立训练环境

不要在固定 Planner 的 `qwen-tf448` 虚拟环境中安装训练依赖：Planner
需要保持 `transformers 4.48.3`，而 TRL 的有状态 `environment_factory`
需要 `transformers>=5.2`。在容器中建立单独虚拟环境：

```bash
cd /workspace/RL-NavGPT/nav_src

TRAIN_VENV=/home/xl/venvs/navgpt-rl
python3 -m venv --system-site-packages "$TRAIN_VENV"
TRAIN_PYTHON="$TRAIN_VENV/bin/python"

"$TRAIN_PYTHON" -m pip install --upgrade pip
"$TRAIN_PYTHON" -m pip install -r ../requirements-train.txt

PYTHONNOUSERSITE=1 "$TRAIN_PYTHON" -c \
  'import gymnasium, transformers, trl; print("gymnasium", gymnasium.__version__); print("transformers", transformers.__version__); print("trl", trl.__version__)'
```

若 `TRAIN_VENV` 已存在，不要重复执行 `python3 -m venv`，直接从
`TRAIN_PYTHON=...` 继续即可。

### 6.2 运行真实数据 smoke test

```bash
cd /workspace/RL-NavGPT/nav_src

TRAIN_PYTHON=/home/xl/venvs/navgpt-rl/bin/python
PLANNER_CACHE=../datasets/R2R/action_plan_cache/qwen2.5-14b-train-t0-v1

PYTHONNOUSERSITE=1 "$TRAIN_PYTHON" scripts/validate_rl_env.py \
  --root-dir ../datasets \
  --split R2R_train_enc \
  --action-plan-cache \
    "$PLANNER_CACHE/R2R_train_action_plans.jsonl" \
  --instr-id 6250_0 \
  --max-steps 20
```

最后必须输出 `PASS instr_id=6250_0`，并通过以下检查：

- 同一 `instr_id` 重置后 action plan、起点、朝向和初始 Prompt 完全一致；
- 相邻移动、非法 ID no-op、回溯、提前停止、成功停止和最大步数截断；
- `terminated` 与 `truncated` 语义正确，成功只由 3m 内主动 `Finish!` 触发；
- 上一步/当前步视觉特征能随 transition 交给后续复合奖励；
- Gymnasium 官方环境检查器通过；
- 同一 GRPO group 的模拟器与奖励状态隔离，同时共享只读导航图缓存；
- 创建 rollout 不改变 Python 全局随机数状态；
- TRL 零参数 factory 只公开一个策略动作入口，不会误公开 Gym 辅助方法；
- `trl_environment_reward()` 能显式读取 episode 累积奖励（TRL 0.29 不会
  自动调用环境的 `get_reward()`）。

第三步的 `stage3_placeholder` 奖励固定为 `0.0` 是预期行为。基础导航、
CLIP 语义对齐和思维质量奖励将在第四步接入同一个 transition，不应提前
混入本次环境状态机验证。

### 7.4 预计算训练扫描的 36 朝向原始视觉特征

这一步会启用 MatterSim rendering，但不会加载 14B。每个 viewpoint 依次
编码 3 个 elevation × 12 个 heading，并按 scan 原子写入，SSH 中断后可用
同一条命令继续；已完成且校验通过的 scan 会显示 `resumed`。

```bash
cd /workspace/RL-NavGPT/nav_src

TRAIN_PYTHON=/home/xl/venvs/navgpt-rl/bin/python
CLIP_MODEL=../models/clip-vit-large-patch14
CLIP_CACHE=../datasets/R2R/clip_cache/openai-clip-vit-large-patch14
ANNOTATION=../datasets/R2R/annotations/R2R_train_enc.json
MATTERPORT_SCANS=$(realpath ../datasets/Matterport3D/v1_unzip_scans)

nohup env CUDA_VISIBLE_DEVICES=0 PYTHONNOUSERSITE=1 PYTHONUNBUFFERED=1 \
  "$TRAIN_PYTHON" scripts/build_clip_cache.py visual \
  --annotation "$ANNOTATION" \
  --connectivity-dir ../datasets/R2R/connectivity \
  --scan-data-dir "$MATTERPORT_SCANS" \
  --model-path "$CLIP_MODEL" \
  --model-id openai/clip-vit-large-patch14 \
  --model-revision main \
  --device cuda \
  --dtype fp16 \
  --batch-size 36 \
  --width 640 --height 480 --vfov 60 \
  --output-dir "$CLIP_CACHE/R2R_train_visual" \
  > "$CLIP_CACHE/R2R_train_visual.log" 2>&1 &

tail -f "$CLIP_CACHE/R2R_train_visual.log"
```

生成完成后目录中会出现 `manifest.json`。如果某个已有 scan 文件损坏，
续跑会拒绝该文件并提示使用 `--overwrite`；模型实际权重 SHA256、revision、
RGB 色彩空间或相机参数任一变化也会拒绝续跑，防止同一目录混入不同来源
的特征。该参数会重建全部训练扫描，不要在仍有生成进程运行时使用。

```bash
MAX_COMPLETION_LENGTH=$(
  "$TRAIN_PYTHON" -c \
  'import json,sys; print(json.load(open(sys.argv[1]))["token_budget"]["recommended_max_completion_length"])' \
  "$VALIDATION_ROOT/level2_report.json"
)

echo "MAX_COMPLETION_LENGTH=$MAX_COMPLETION_LENGTH"
```

### 11.3 Level 3：真实 14B Trainer 与单组 rollout

确认 GPU 空闲后执行。`CUDA_VISIBLE_DEVICES=2` 后进程中的物理 GPU 2 会显示
为逻辑 `cuda:0`；CLIP 和 Qwen 都使用这一逻辑设备。

```bash
TRAIN_PYTHON=/home/xl/venvs/navgpt-rl/bin/python
VALIDATION_ROOT=$(cat /tmp/navgpt-stage6-validation-root)

PYTHONNOUSERSITE=1 CUDA_VISIBLE_DEVICES=2 \
  PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
  "$TRAIN_PYTHON" scripts/validate_grpo_levels.py level3 \
  --validation-root "$VALIDATION_ROOT"
```

本级加载一次 14B，构造真实 `GRPOTrainer`，为同一任务生成并评分四条 rollout；
不执行 backward/optimizer step，也不写训练 checkpoint。最后必须输出
`PASS stage-six validation level 3`，并列出四条 completion token、tool call、
advantage 和显存峰值。如果四条都没有调用导航工具，本级会失败，不允许把
纯文本生成误认为环境 rollout。

### 11.4 Level 4：短训练与断点等价性

本级最耗时，会顺序启动三个独立 Python 进程并各加载一次 14B：连续训练到
step 2、训练到 step 1 后停止、从 `checkpoint-1` 恢复到 step 2。任一时刻
仍只有一份 14B 模型驻留 GPU。建议在 `tmux` 中执行：

```bash
TRAIN_PYTHON=/home/xl/venvs/navgpt-rl/bin/python
VALIDATION_ROOT=$(cat /tmp/navgpt-stage6-validation-root)

PYTHONNOUSERSITE=1 CUDA_VISIBLE_DEVICES=2 \
  PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True \
  "$TRAIN_PYTHON" scripts/validate_grpo_levels.py level4 \
  --validation-root "$VALIDATION_ROOT"
```

最后必须输出：

```text
PASS stage-six validation level 4
- uninterrupted 2-step run equals 1-step + checkpoint resume
- LoRA tensors=... max_abs_difference=0; optimizer/scheduler/RNG/rollouts identical
```

四级全部通过后，正式训练使用 Level 2 报告中的
`recommended_max_completion_length`，而不是 Level 3/4 为缩短烟雾测试而
自动计算的一轮工具预算。Level 4 目录含两条短训练分支和完整 checkpoint，
用于审计，不应当作正式训练的初始化 adapter。
